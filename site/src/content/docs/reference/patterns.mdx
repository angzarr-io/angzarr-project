## Delivery Patterns

### Outbox Pattern

> **You probably don't need this.** Modern managed messaging (Kafka, SQS, Pub/Sub) already guarantees delivery. Only consider outbox if your messaging layer lacks durability.

The outbox pattern ensures atomicity between database writes and event publishing:

```text
1. Events persisted to event store  }
2. Events written to outbox table   }  ← Single transaction
3. Background process polls outbox
4. Events published to message bus
5. Outbox entries marked published
```

**When to use:**
- In-memory or non-durable message transport
- Regulatory requirement for local audit trail

**Skip when using:**
- Kafka with `acks=all`
- AWS SQS/SNS
- GCP Pub/Sub
- RabbitMQ with persistent queues

### Idempotent Consumer

Consumers must tolerate duplicate events. Design for natural idempotency:

| Operation | Idempotent? | Fix |
|-----------|-------------|-----|
| `INSERT` | No | Use `INSERT ... ON CONFLICT DO NOTHING` |
| `UPDATE SET x = x + 1` | No | Use absolute: `UPDATE SET x = $value` |
| `UPDATE SET x = $value` | Yes | Already idempotent |
| `DELETE WHERE id = $1` | Yes | Already idempotent |

⍼ Angzarr's sequence numbers ensure events are never applied twice—both deltas (`amount: 50`) and absolute values (`new_balance: 150`) are idempotent.

## Schema Evolution

### Upcasting

Transform old event versions to current version when reading:

<Tabs>
<TabItem label="Python">

```python
class PlayerRegisteredV1ToV2Upcaster:
    def can_upcast(self, event_type: str, version: int) -> bool:
        return event_type == "PlayerRegistered" and version == 1

    def upcast(self, event: dict) -> dict:
        # V1 had "name", V2 split into "first_name" and "last_name"
        name_parts = event["name"].split(" ", 1)
        return {
            "first_name": name_parts[0],
            "last_name": name_parts[1] if len(name_parts) > 1 else "",
            "email": event["email"],
        }
```

</TabItem>
</Tabs>

**Key points:**
- Stored events remain unchanged
- Transformation happens on read
- Enables gradual schema migration

## Coordination Patterns

### Correlation ID

Links related events across aggregates:

```protobuf file=proto/io/angzarr/v1/types.proto region=cover
```

**Propagation rules:**
- Client provides correlation_id on initial command (if cross-domain tracking needed)
- Framework does NOT auto-generate—if not provided, stays empty
- Once set, propagates through policies and process managers

### Conflict Resolution

Optimistic concurrency, per stream: a command may name the stream head it was decided against (`Handling.expected_sequence`), and its conflict resolution says what happens when the stream has moved on since. Three resolutions exist, `STRICT`, `AGGREGATE_HANDLES` and `COMMUTATIVE`; the authoritative rules are the `ConflictResolution` region and `Handling.expected_sequence` in `io/angzarr/v1/types.proto`.

In short:

- **`STRICT`**: a command behind the head is refused `ABORTED`, `COORDINATOR_REASON_EXPECTED_SEQUENCE_STALE`, before business code. The caller re-reads and re-decides (decision 14.45).
- **`AGGREGATE_HANDLES`**: business code receives the events the command did not see (the window) with a nonce, and applies its own conflict rule; one that never resolves the window fails `ABORTED`, `COORDINATOR_REASON_CONFLICT_UNRESOLVED`.
- **`COMMUTATIVE`**: delivered like `AGGREGATE_HANDLES`, but the client library computes the conflict units the window and the command changed, and the coordinator keeps the command's events only if they are disjoint; an overlap fails `ABORTED`, `COORDINATOR_REASON_CONFLICT_OVERLAP` (decision 14.42).
- **Every resolution**: an expected sequence *ahead* of the head is malformed, refused `INVALID_ARGUMENT`, `COORDINATOR_REASON_EXPECTED_SEQUENCE_AHEAD` (decision 14.47).

Which resolutions a stream supports comes from its registered state: every state supports `STRICT` and `AGGREGATE_HANDLES`, and `COMMUTATIVE` only where the state declares conflict units (the `conflict_units` region of `io/angzarr/v1/options.proto`). With none chosen, the default is `COMMUTATIVE` where supported and `STRICT` otherwise. A command without an expected sequence is stamped with the head it decides against, so it is never stale: if it loses a race at its write, the coordinator re-runs it on the new head, under the race re-run cap (decision 14.46).

What each status means to a caller, which class it belongs to (decision 14.37) and what happens at a retry cap: see [Error Recovery](/operations/error-recovery).

### Command Modes

How much of a command's processing returns to the caller is chosen by the RPC called:

| RPC | Mode | Projectors | Policies | Use Case |
|-----|------|------------|----------|----------|
| `HandleAsync` | ASYNC | Async | Async | Fire-and-forget: validated and enqueued, nothing about the decision comes back |
| `Handle` | DECISION | Async | Async | Accept or reject synchronously; returns the persisted events |
| `HandleSync` | SIMPLE | Sync | Async | Read-after-write: also waits for the domain's synchronous projectors |

No mode waits for reactions. Policies always run asynchronously, after the command's events are persisted, and the commands they send are separate commands with their own outcomes. Every mode publishes the persisted events downstream: there is no mode that writes silently. (Synchronous cascades were removed, decision 2.1: they coupled aggregates' availability and hid partial failure.)

## Query Patterns

### Temporal Query

Reconstruct state at any point in history:

```python
# Get player balance as of yesterday
events = event_store.get_events(
    domain="player",
    root=player_id,
    up_to_timestamp=yesterday,
)
state = build_state(events)
print(f"Balance at {yesterday}: {state.bankroll}")
```

**Enabled by:**
- Immutable event stream
- Events contain absolute state
- No destructive updates

## Advanced Patterns

### Edition / Branching

**Use cases:**

| Scenario | How |
|----------|-----|
| **What-if analysis** | Branch at sequence N, apply hypothetical commands |
| **Historical branches** | Explore alternative histories |
| **Policy coordination** | Reactions stay in their trigger's edition, and fork the streams they reach |
| **Speculative execution** | Execute commands speculatively, merge or discard |

**Per-stream forks** (decisions 14.32 and 14.35): forking an origin stream starts the edition; the fork travels with the data, each policy command forking the stream it reaches at that stream's head. There is no global position, so there is no fork at one store-wide moment.

```python
# Create a what-if branch by forking the player's stream
cover = Cover(domain="player", root=player_id, edition="bonus-scenario")
admin.fork_stream(cover)

# Commands on this cover write to the branch, not main timeline
cmd = CommandBook(cover=cover, page=...)  # exactly one command per book
```

### Snapshot Retention

**When to use:**

| Retention | Use Case | Example |
|-----------|----------|---------|
| **DEFAULT** | Normal operation; deleted when a newer snapshot is written | Most events |
| **PERSIST** | Business milestones | End-of-day balance, audit checkpoints |
| **TRANSIENT** | Temporary optimization | Intermediate computation state |

**Snapshot with retention:**

```python
# Mark a snapshot as a business milestone (never delete)
snapshot = Snapshot(
    sequence=current_sequence,
    state=state.SerializeToString(),
    retention=SnapshotRetention.RETENTION_PERSIST,
)
```

## Component Coordination

### Policy vs Process Manager

| Aspect | Policy | Process Manager |
|--------|------|-----------------|
| **State** | Stateless | Own event stream |
| **Input** | Single domain | Multiple domains |
| **Identity** | None | correlation_id |
| **Timeouts** | No | Yes |

**Rule of thumb:** Start with policies. Upgrade to PM when you need state or multi-domain input.
