A **process manager** coordinates multi-domain workflows with state tracking. Unlike stateless sagas, process managers maintain their own event stream keyed by correlation ID, enabling complex orchestration patterns.

A process manager **is a domain**. Like any domain it takes **commands**, which it may refuse, and **facts** (timeouts, webhooks, rejection facts), which it never refuses. It subscribes to no domain: when it must hear what happened in another domain, a saga from that domain turns the event into a command to it. Everything it emits is its own events: to act on another domain it records an event carrying the data that domain's command needs, and a saga from the PM's domain builds the command. It is served exactly as an aggregate is, by the same command-handler services.

---

## When to Use Process Managers

| Use Case | Saga | Process Manager |
|----------|------|-----------------|
| Single event → single command | ✓ | |
| Fan-out to multiple domains | ✓ (one saga per destination) | |
| Multi-step workflow with state | | ✓ |
| Gathers what happened in several domains (as facts, through sagas) | | ✓ |
| State machine transitions | | ✓ |
| Timeouts and retries | | ✓ |

### Warning: Process Manager Anti-Patterns

**Over-reliance on process managers is a foot-gun.** If you find yourself:

- Putting significant business logic in a PM
- Building PMs with large, complex state
- Creating PMs for workflows within a single domain
- Reaching for PMs as a first solution

**Your domain factoring is probably wrong.**

Process managers should be **lightweight state machines** coordinating across domains—not business logic containers. They answer "what phase are we in?" and "what happens next?", not "how do we calculate X?"

| Symptom | Likely Problem |
|---------|----------------|
| PM has complex validation logic | Logic belongs in domain aggregate |
| PM state mirrors aggregate state | Redundant—query the aggregate |
| PM handles single-domain workflow | Use saga or aggregate instead |
| PM event stream grows large | Too much responsibility—split domains |

**Rule of thumb:** If a PM does more than track phases and record what should happen next, reconsider your architecture. The PM's job is orchestration, not computation.

## Example: Hand Flow PM

The HandFlowPM orchestrates poker hand phases across table and hand domains. Sagas into its domain tell it what happened, as commands; it records each next step as its own event; sagas from its domain turn those events into commands:

```mermaid

    participant SI as Sagas into hand-flow
    participant PM as HandFlowPM
    participant SO as Sagas from hand-flow
    participant H as Hand

    T-->>SI: HandStarted
    SI->>PM: StartHandFlow (a starting command)
    PM->>PM: records DealRequested
    PM-->>SO: DealRequested
    SO->>H: DealCards
    H-->>SI: CardsDealt
    SI->>PM: RecordCardsDealt
    PM->>PM: records the phase change
    H-->>SI: HandComplete
    SI->>PM: RecordHandComplete
    PM->>PM: records HandFinished
    PM-->>SO: HandFinished
    SO->>T: EndHand
```

## Correlation ID

Process managers use the **correlation ID** as their aggregate root:

```protobuf file=proto/io/angzarr/v1/types.proto region=cover
```

The PM instance's root **is** the workflow's correlation ID, unchanged. A command or fact addressed to a PM names its instance: its cover is the PM's domain with the instance's correlation ID as its root (and its `correlation_id` must agree). A saga that tells a PM about an event addresses the instance that event's correlation names. All events in a workflow share the same correlation ID, allowing the PM to:
- Hear, through sagas, what happened in several domains
- Maintain workflow state across its inputs
- Track progress through the state machine
- Record the data each next step needs, for a saga to send on

### Which inputs start an instance

A PM declares which of its command and fact types are **starting** inputs (`starts` on the `(command)` entry). An input for a correlation the PM has no instance for starts one only if its type is a starting input. Any other such fact is skipped, silently: nothing is recorded, dead-lettered or alerted, and the sender is answered `APPLIED` with no events. Any other such command is refused (`FAILED_PRECONDITION`, `PM_NO_INSTANCE`), recording nothing. Declare as starting every input that can arrive first: inputs from different domains arrive in no guaranteed order.

## Commands In, Its Own Events Out

| | What it is | Who sends it |
|-|-----------|--------------|
| **Input: a command** | A request the PM may refuse | A saga from another domain (turning that domain's event into a command), or a client |
| **Input: a fact** | Something that already happened, never refused | A timer or webhook, or a refusal fact from a saga from the PM's domain |
| **Output: its own events** | What the PM decided, with the data the next step needs | Sagas from the PM's domain turn them into commands |

```python title="illustrative"
# The saga from "hand" to the PM's domain tells the PM, as a command.
def on_hand_complete(event: HandComplete, ctx: SagaContext):
    return CommandBook(domain="hand-flow", root=ctx.correlation_id,
                       command=RecordHandComplete(winner_root=event.winner_root,
                                                  pot=event.pot))
```

Its only output is its own events. To act on another domain, it records an event that carries the command's data, and the saga for (the PM's domain, that domain) builds the command:

```python title="illustrative"
# The PM records what should happen next, with the data the command needs.
def handle_hand_complete(cmd: RecordHandComplete, state: WorkflowState):
    return PotAwarded(player_root=cmd.winner_root, amount=cmd.pot)

# The saga from the PM's domain to "player" builds the command.
def on_pot_awarded(event: PotAwarded):
    return CommandBook(domain="player", root=event.player_root,
                       command=TransferChips(amount=event.amount))
```

The coordinator, not the handler, deduplicates, as for any domain: a redelivered command or fact is found on the PM's stream by its id before the handler runs, and the handler is not called again. A saga's command gets its id from the event it reacts to, so a saga re-run sends the same id.

## State Persistence

PM state is stored as events in the PM's own event stream:

```text title="illustrative - PM event stream"
PM Event Stream (correlation_id = "hand-abc-123"):
  [0] WorkflowStarted { hand_id: "...", phase: "awaiting_deal" }
  [1] PhaseTransitioned { from: "awaiting_deal", to: "dealing" }
  [2] PhaseTransitioned { from: "dealing", to: "blinds" }
  [3] WorkflowCompleted { winner_id: "..." }
```

On restart, the PM rebuilds state by replaying its own events.

## Replies and Refusals

A PM tracks the replies to the steps it starts. Its event carries the instance's correlation ID, so the saga's command built from it carries that correlation, and so do the target's events. The saga from the target's domain to the PM's domain turns the replies the PM needs into commands to the instance under that correlation.

A target that **refuses** a saga's command records nothing. The saga delivers one **refusal fact** to its own source domain; when that source is the PM, the PM decides the next step from its own state. The fact's id is the refused command's id. Two modes, chosen per command when the code is generated (the `angzarr` CLI's refusal switch; the proto gives the default):

- **Pass-through (default).** The saga's generated code forwards the standard `CommandRefused { command, response, trigger }`. The PM lists the foreign command in its `refusals` and gets a generated handler:

  ```python title="illustrative"
  # BuyInState: refusals: "examples.v1.HoldFunds"
  def on_refused_hold_funds(refusal: CommandRefused, state: BuyInState):
      return BuyInFailed(buy_in_id=state.buy_in_id,
                         reason=refusal.response.message)
  ```

- **Translate (opt-in).** The saga's `sends` entry names a domestic `refusal_fact`, and the saga's callback translates the refusal, so the PM never refers to the foreign protos:

  ```python title="illustrative"
  # BuyInTableSaga: sends {command: "ConfirmSeat", refusal_fact: "SeatConfirmationRefused"}
  def on_refused_confirm_seat(refusal: Refusal) -> SeatConfirmationRefused:
      return SeatConfirmationRefused(buy_in_id=refusal.command.buy_in_id,
                                     reason=refusal.response.message)
  ```

The refusal fact is unrefusable, so compensation cannot loop. There is no notification or compensation channel. A hard failure of the saga's command (anything but a business rejection) is retried when retryable and otherwise dead-lettered, as for any saga command.

## PM vs Saga

| Aspect | Saga | Process Manager |
|--------|------|-----------------|
| **State** | Stateless | Stateful (own event stream) |
| **Identity** | None | correlation_id |
| **Input** | Events of its one source domain | Commands and facts addressed to it (subscribes to no domain) |
| **Output** | Commands for its one destination (an aggregate's or a PM's domain); a refusal fact for its own source when one is refused | Its own events only |
| **Owned stream** | None (`domain` must be empty) | Its own workflow domain (`domain` required) |
| **Persistence** | No | Yes (workflow events) |
| **Timeouts** | No | Planned |
| **Complexity** | Low | Higher |

A component declares three separate domain roles in `ComponentOptions`: `domain` is the stream it owns, `input_domain` / `(event).domain` are the domains it subscribes to, and `output_domain` is the one domain a saga sends to. A process manager declares only `domain`: it subscribes to nothing and sends nothing but its own events.

**Rule of thumb**: Start with sagas. Upgrade to PM when you need state tracking across steps or what happened in several domains.
