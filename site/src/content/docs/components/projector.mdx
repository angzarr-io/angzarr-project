A **projector** subscribes to events and performs side effects—typically building read models, writing to databases, or streaming to external systems. Projectors transform the event stream into query-optimized views.

Unlike aggregates and sagas, projectors are **read-only** from the event sourcing perspective. They observe events but never emit commands back to aggregates.

---

## Common Use Cases

| Projector | Events | Output |
|-----------|--------|--------|
| Search indexer | Product events | Elasticsearch updates |
| Dashboard stream | All domain events | WebSocket push |
| Analytics ETL | Transaction events | Data warehouse |
| Cache warmer | Player events | Redis cache |
| Money ledger | Wallet and table events | Balances and a balanced flag |

---

## Canonical Style

Projectors are defined as classes extending the client library's `Projector` base (or the language's closest equivalent). Handler methods are registered by decorator / attribute / macro and share the instance's state.

---

## Example: Ledger Projector

The blackjack example's ledger folds wallet and table events into balances, and reports whether all the money adds up:

<TabItem label="Python">

```python title="illustrative - blackjack ledger projector (excerpt)"
@projector(name="projector-player-table-ledger", domains=["player", "table"])
class LedgerProjector:
    """Money read model over wallets and tables."""

    def __init__(self) -> None:
        self.ledger = LedgerProjection()
        self._applied: set[tuple[str, bytes, int]] = set()

    def _first_time(self, domain: str, root: bytes, sequence: int) -> bool:
        key = (domain, root, sequence)
        if key in self._applied:
            return False  # replay or redelivery: already applied
        self._applied.add(key)
        return True

    @projects(player_pb2.FundsDeposited)
    def on_funds_deposited(self, event, root: bytes, sequence: int) -> None:
        if self._first_time("player", root, sequence):
            self.ledger.players[root.hex()].bankroll += event.amount
            self.ledger.totals.deposits += event.amount
            self.ledger.totals.bankrolls += event.amount

    @projects(table_pb2.RoundSettled)
    def on_round_settled(self, event, root: bytes, sequence: int) -> None:
        if self._first_time("table", root, sequence):
            table = self.ledger.tables[root.hex()]
            table.house_result = event.house_result_after
            ...
```

## Multi-Domain Projectors

Projectors **can** subscribe to events from multiple domains, but **should not** unless absolutely required:

```python title="illustrative"
# Avoid this pattern when possible
class AuditProjector(Projector):
    domains = ["player", "table"]

    @projects(PlayerRegistered)
    def on_player_registered(self, event): ...

    @projects(RoundSettled)
    def on_round_settled(self, event): ...
```

**If you need multi-domain subscription, check your domain boundaries first.** Needing to join events across domains often indicates the domains are incorrectly partitioned. Consider whether those events belong in the same domain.

When multi-domain is truly necessary (e.g., a cross-cutting view such as the example's money ledger, which must see both sides of every transfer), it's technically safe because projectors only observe—but prefer single-domain projectors where possible for simpler reasoning and deployment.

## Synchronous vs Asynchronous

| Mode | Use Case | Behavior |
|------|----------|----------|
| **Async** (default) | Analytics, search indexing | Fire-and-forget |
| **Sync** | Read-after-write | Command waits for projector |

Synchronous projections enable CQRS patterns where commands must return updated read models.

---

## Position Tracking

Projectors track their position in the event stream to enable:
- **Catch-up**: Resume from last processed event after restart
- **Replay**: Rebuild read models from scratch

The framework manages position tracking automatically.
