title: Saga Examples
---

Cross-domain translations from the blackjack example. Each saga is stateless: it takes target roots from fields of the source event, never looks anything up, and emits deferred commands (which the destination may refuse) or facts (which it must accept).

:::note
The blackjack implementations are being written. Until the Python one lands, this page shows the example's specification rather than saga code.
:::

---

## Saga: Player → Table (a command that can be refused)

A **top-up** starts in the wallet: `TopUpRequested{hold_id, table_root, amount}` becomes the table's `AddChips{player_root, hold_id, amount}`. The table may refuse — for example while the player has a bet in play.

```protobuf title="proto/io/angzarr/examples/blackjack/v1/sagas.proto (excerpt)"
message PlayerTableSaga {
  option (io.angzarr.v1.component) = {
    kind: COMPONENT_KIND_SAGA
    input_domain: "player"
    output_domain: "table"
  };
}
```

---

## Saga: Compensation

When the table refuses `AddChips`, the refusal is delivered back to the wallet, which releases its hold. The wallet declares it with `compensates: "io.angzarr.examples.blackjack.v1.AddChips"`, which generates an `OnAddChipsRejected` handler.

```gherkin title="features/example/blackjack-framework/saga.feature (excerpt)"
Scenario: A top-up the table refuses is undone in the wallet
  Given "Alice" is registered with 1000 deposited
  And "Alice" asked to top up 200 at table "Main" with request "T1"
  And "Alice" has a bet in play at table "Main"
  When table "Main" handles the request to add chips from top-up "T1"
  Then the request is refused because a wager is in play
  And the wallet of "Alice" is told the request was refused
  And the top-up "T1" is refused with reason "WAGER_IN_PLAY"
  And "Alice" has a bankroll of 1000 with 1000 available
```

## Saga: Table → Player (facts)

Chips added at the table and a player's cash-out are already decided. The settlement saga turns them into facts the wallet records exactly once, keyed by the hold or cash-out id:

```gherkin title="features/example/blackjack-framework/saga.feature (excerpt)"
Scenario: Delivering the same cash-out twice credits it once
  Given "Alice" is registered with 1000 deposited
  And "Alice" cashed out 640 from table "Main"
  And the settlement translator has handled the cash-out
  When the settlement translator handles the same cash-out again
  Then the second delivery is recognised as already recorded
  And "Alice" has a bankroll of 1640 with 1640 available
```

## Saga Principles

1. **Stateless** — Each event processed independently
2. **Minimal logic** — Just translate fields between domains
3. **Single source** — Events from one domain only
4. **Single target** — Commands to one domain only
5. **No destination state** — Emit deferred commands; the destination appends them at its head
