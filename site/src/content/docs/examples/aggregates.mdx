title: Aggregate Examples
---

The example domain is a small blackjack table with two aggregates: the **player** wallet and the **table**. Their behaviour is specified once, in protos and Gherkin scenarios in [angzarr-project](https://github.com/angzarr-io/angzarr-project), and implemented in all six languages against the same scenarios.

:::note
The blackjack implementations are being written. Until the Python one lands, this page shows the example's specification rather than handler code.
:::

All aggregates in all six languages use the **OO pattern**: a class derived from the client library's `CommandHandler<State>` with `@handles` for command dispatch and `@applies` for event-to-state application (naming adapted per language idiom). Every handler follows guard → validate → compute as pure functions.

---

## Commands and events are declared in proto

A command names the aggregate state message that handles it; an event names every component that consumes it. The player wallet's hold commands, from `player.proto`:

```protobuf title="proto/io/angzarr/examples/v1/player.proto (excerpt)"
// Earmark funds for a buy-in. hold_id is the buy_in_id.
message HoldFunds {
  option (io.angzarr.v1.command) = { component: "io.angzarr.examples.v1.PlayerState" };
  bytes hold_id = 1;
  bytes table_root = 2;
  int64 amount = 3;
}

// A buy-in hold was opened.
message FundsHeld {
  option (io.angzarr.v1.event) = { component: "io.angzarr.examples.v1.PlayerState" };
  option (io.angzarr.v1.event) = { component: "io.angzarr.examples.v1.BuyInState" domain: "player" };
  option (io.angzarr.v1.event) = { component: "io.angzarr.examples.v1.LedgerProjection" domain: "player" };
  bytes hold_id = 1;
  bytes table_root = 2;
  int64 amount = 3;
}
```

`FundsHeld` is folded into the wallet's own state, triggers the buy-in process manager and is projected into the ledger — one event, three consumers.

## Two-phase holds

The wallet never moves money when it holds it: a hold only earmarks part of the bankroll. The money leaves when the hold is captured (buy-in) or settled (top-up), and a hold that does not go through is released.

```gherkin title="features/example/blackjack/player.feature (excerpt)"
Scenario: Holding funds reduces what is available but not the bankroll
  Given player "Alice" is registered with 1000 deposited
  When 500 of "Alice"'s funds are held for buy-in "B1" at table "Main"
  Then "Alice" has a bankroll of 1000 with 500 available
  And "Alice" has an open hold "B1" of 500 for table "Main"
  And the wallet of "Alice" balances

Scenario: A hold larger than the available balance is refused
  Given player "Alice" is registered with 1000 deposited
  And 700 of "Alice"'s funds are held for buy-in "B1" at table "Main"
  When 500 of "Alice"'s funds are held for buy-in "B2" at table "Side"
  Then the hold is refused because "Alice" has only 300 available
```

Repeating an identical hold succeeds with no events, so a redelivered request is harmless.

## Multi-event commands

The table runs a whole round inside one aggregate. `DealRound` may emit a new shoe, the deal, and — when nobody can act — the dealer's play and the settlement, all in one step. The action that finishes the last hand does the same:

```gherkin title="features/example/blackjack/round.feature (excerpt)"
Scenario: The last action plays the dealer and settles in the same step
  Given "Alice" has bet 20 at seat 0
  And the shoe begins "10♣ 10♦ 9♥ 7♠"
  And the round has been dealt
  When "Alice" stands at seat 0
  Then the table records, as one step, that seat 0 stood, the dealer played and round 1 was settled
```

## Testing

⍼ Angzarr uses **Gherkin feature files as living specifications**. The same feature files run against all language implementations. Because `@handles` methods are ordinary methods, they also test directly: construct the aggregate, seed its prior events, invoke the method, assert on the returned events.

See **[Testing](/operations/testing)** for the full testing strategy.
